# Raff-SEO-GEO audit checklist

This checklist is conditional: use only checks relevant to the site and request. The links point to primary sources; recheck current guidance when a rule may have changed. If data or access is unavailable, report that limit instead of inferring that the feature or result is absent. Finish with available code, public-site evidence, and history; private dashboards and exports enrich the audit but are never prerequisites. Do not start account connection or authentication flows.

## Goal, coverage, and opportunities

- Apply the [intent research method](intent-research.md) and retain a need-to-page map proportionate to the scope. Link supported opportunities to the common action queue. Preserve technical observations using the [collection guide](collection.md), including dates, request context and evidence locators for later comparisons.
- Connect the audience and useful outcome to important pages and user needs. Record the pages/templates examined, why they were selected, and what was not examined. On a small site, inspect the relevant pages directly; on a larger site, disclose sampling and group shared causes without losing affected URLs. Do not describe untested pages, languages, devices, or engines as verified.
- Look for unmet needs and a distinctive contribution: real examples, original data, demonstrations, tools, direct experience, or explanations specific to this site. Use actual site content, supplied user questions, and public search results when useful. Label an inferred need as a hypothesis when user demand is not observed; never invent volumes.
- When inspecting search results or competing pages, record query, engine, date, locale, and access limits. Use them to understand intent, available answers, and gaps; do not infer that copying a competitor's format or content will produce its ranking. Check existing coverage before recommending a new page; prefer improving a relevant page when it can meet the need. [Google's AI guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) and [helpful-content guide](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) ground the focus on original, useful content, not a guaranteed result.
- Examine whether a visitor can understand the offer and reach the intended action. Distinguish an observed broken or confusing path from an assumed conversion problem. Make opportunity recommendations specific to a need, page, evidence, expected contribution, and verification method.

## Access and indexing

1. On important pages, check HTTP status, redirects, intended canonical version, access without signing in, `noindex`/`nosnippet` directives, `robots.txt`, and any CDN blocks. Check that HTTP resolves to HTTPS, the certificate is valid, and the HTTPS page serves no mixed-content resources: [HTTPS setup guide](https://web.dev/articles/enable-https), the page Google's former HTTPS article now redirects to. `robots.txt` controls crawling, not privacy or deindexing by itself; a crawler must be able to read `noindex`: [Google](https://developers.google.com/search/docs/crawling-indexing/robots/intro), [Bing](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a).
2. Compare served HTML, browser rendering, and, if available, rendering inspected in the search engine's tool, especially for JavaScript applications. Check that essential content is accessible and readable as text; do not infer search-engine rendering from code alone: [Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics), [Google AI guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).
3. Check HTML internal links to important pages, navigation, duplicates, and canonical/redirect consistency. A canonical is a signal, not an absolute instruction: [Google](https://developers.google.com/search/docs/crawling-indexing/canonicalization), [Bing](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a).
4. If meaningful URLs need discovery, check the sitemap: canonical, indexable URLs; availability; `lastmod` reflecting a real change; and reference in `robots.txt` or submission through the engine's tool. A sitemap aids discovery without guaranteeing indexing: [Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), [Bing](https://blogs.bing.com/webmaster/July-2025/Keeping-Content-Discoverable-with-Sitemaps-in-AI-Powered-Search).

## Content and presentation

5. For each page, examine the reader's need, useful answer, accuracy, first-hand experience or site-specific evidence, date when relevant, explanatory links, and duplicate content. Check identifiable authors or organizations, appropriate sourcing, and evidence for expertise where readers need it; do not invent credentials or treat an author box as a ranking switch. Avoid mass-produced pages that target minor query variants; structure content for readers, without a mandatory word count or “AI” format: [Google helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [Google AI guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).
6. Check distinct, descriptive page titles; useful descriptions; clear sections; and relevant images with suitable alt text. Compare mobile and desktop: essential content, titles, metadata, indexing directives, and structured data should remain equivalent when the versions differ. `og:image` may help Google choose a preview image, but is not evidence of a ranking effect: [Google SEO guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide), [mobile indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing), [Google Images](https://developers.google.com/search/docs/appearance/google-images).
7. If equivalent pages exist for multiple languages or regions, check `hreflang` annotations, their URLs, and return links; do not add them to a single-language site without variants: [Google](https://developers.google.com/search/docs/specialty/international/localized-versions).
8. Check real user experience (readability, mobile navigation, latency, stability, and accessibility) with available tools and data; do not turn a laboratory score into observed traffic or citations: [Google page experience](https://developers.google.com/search/docs/appearance/page-experience).

## Enhancements and AI search engines

9. Consider structured data only for a currently documented use, with truthful properties appropriate to the page. Apply the [decisions guide](decisions.md) to unsupported or retired tactics. For a rich result, check required properties, matching visible content, quality rules, and syntax with the Rich Results Test when it supports the type. Other documented uses, such as `Organization` for identity clarity or `primaryImageOfPage` to suggest an image, are not promises of a rich result or ranking. Keep site-wide entity markup on the home page or the single page describing the organization: Google states you do not need it on every page, and `url` is what helps it identify the organization uniquely, so one organization must not be emitted with a `url` that varies by page or locale. Check repeated blocks for conflicting identifying values; declare language variants with `hreflang` (step 7) and other profiles with `sameAs`, not with duplicate organizations: [Google gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery), [policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [Organization](https://developers.google.com/search/docs/appearance/structured-data/organization), [Images](https://developers.google.com/search/docs/appearance/google-images).
10. If ChatGPT Search is in scope, inspect `OAI-SearchBot` and any observable network blocks, separately from training choices. Apply the [decisions guide](decisions.md) for crawler distinctions. If logs are supplied, check request identity against the provider's published verification information rather than trusting a user-agent string alone. A successful fetch with a spoofed user-agent does not prove access by the real crawler: [OpenAI](https://developers.openai.com/api/docs/bots).
11. For Google AI Overviews and AI Mode, check observable technical eligibility: indexing, directives, and accessible rendering. Eligibility also depends on the account-level **Search generative AI** control, which is only visible in Search Console and outside this audit's scope; state it as unknown rather than checking or changing it. Do not confuse it with `Google-Extended`, which concerns training and is a separate control. No special file or schema is required: [Google AI guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).
12. For Bing/Copilot, check indexing and the directives Bing supports for content shown or used in Copilot; do not transfer Google rules automatically. If the site changes frequently, consider IndexNow to notify the engine about added, updated, or deleted URLs, without promising crawling or indexing: [Bing guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a), [IndexNow](https://www.bing.com/indexnow/getstarted).

For Perplexity and Claude, use the [provider-specific guide](perplexity-claude.md) when either is in scope. Check search access independently of training and user-directed retrieval; state documentation conflicts and actual visibility limits. No private provider account is required.

13. If the site sells products or represents a local business, check relevant Merchant Center or Google Business Profile information and, for Bing local search, Bing Places. These services are context-dependent options, not prerequisites for every site or guarantees of citation: [Google AI guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide), [Bing AI Performance](https://blogs.bing.com/webmaster/February-2026/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview).

## Conditional investigations

- **Traffic incident or migration:** when a decline is reported, establish its dates and affected pages before guessing a cause. Inspect relevant changes, redirects, URL mappings, availability, and indexing directives. Manual actions and security issues are Search Console-only signals outside this audit's scope; state them as unknown rather than checking for them. Do not diagnose a penalty from a traffic graph alone. Consider seasonality, reporting changes, and external demand: [Google traffic-drop guide](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops), [site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).
- **Commerce or large catalog:** inspect applicable product availability, variant/canonical consistency, navigation, and filter URLs. Escalate crawl-budget or faceted-navigation investigations only when scale or observed URL proliferation justifies them: [ecommerce](https://developers.google.com/search/docs/specialty/ecommerce), [faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation).
- **Local business:** review accurate public identity, contact/location information, and existing business listings when accessible. Do not treat opening a private dashboard or creating listings as required for finishing an audit.
- **Documentation or editorial site:** examine version accuracy, useful archives, authorship, internal discovery, and competing pages serving the same need. Assess any consolidation using the decisions guide, not a rule to delete older pages.
- **Image/video-led content:** inspect discoverability, textual context, and applicable media metadata: [Google Images](https://developers.google.com/search/docs/appearance/google-images), [Google video](https://developers.google.com/search/docs/appearance/video). Add no media merely to satisfy a checklist.

## Validation and measurement

14. After a change, run project tests, inspect HTML and rendered pages, then verify the production response after deployment if the user authorized deployment. Distinguish local validation, deployment, indexing, and appearance in an AI answer. For a review-only request, inspect a provided accessible public URL read-only; otherwise state the audit's limit.
15. This skill does not use Search Console or Bing Webmaster Tools. Treat query volumes, AI-impression counts, and citation counts as unmeasured; a `site:` query or a single fetch is a sample, not exhaustive proof of indexing. Rely on the observable technical criteria already inspected and the manual AI-answer observations below for evidence of actual inclusion.

For manual AI-answer observations, record engine/product, date, exact question, locale, relevant session context, returned answer, and cited URL when available. Distinguish mentions, linked citations, referrals, and useful outcomes. A single answer or a small prompt sample is not a population citation rate, universal position, or causal test.

For each proposed action, distinguish **implementation verification** (what can be checked in code or public production) from **outcome measurement** (what happened to users or search visibility). Define an available baseline, source, period, metric, and comparable follow-up when data allows. Record deployment dates and other changes; account for seasonality, devices, countries, and changes in measurement definitions. Do not substitute the code change date for deployment, or assign an improvement to the intervention merely because it followed it.

Without private statistics, use observable acceptance criteria, label business/search outcomes unmeasured, and complete the report. An optional export may be useful for a specific unresolved decision; it is not a required action list item or a reason to withhold justified recommendations.
